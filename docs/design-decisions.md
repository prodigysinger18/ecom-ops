# 设计取舍与面试追问

## 当前系统的真实定位

内部电商客服辅助原型：真实百炼 Embedding/生成，模拟商品订单数据库，人工审核后手动发送建议回复。没有闲鱼平台同步，没有生产用户认证，也没有已验证的生产并发 SLA。

## 为什么选择这些方案

| 决策 | 当前理由 | 代价与替换条件 |
| --- | --- | --- |
| SQLite 本地验收 | 无外部服务即可跑通，方便隔离测试和故障注入 | 不证明生产并发写能力；上线前完成目标数据库迁移、索引、事务、备份及性能验证 |
| SQLAlchemy 统一访问 | 业务查询/事务可复用，测试用临时库 | ORM 不能消除不同数据库的行为差异；应在目标数据库做集成测试 |
| 关键词路由作为基线 | 简单、可解释、耗时低，适合先明确业务边界 | 新候选集107/120，存在自然表达漏判；下一轮用独立开发集优化，不针对最终测试集逐句加词 |
| 普通FAQ直接检索 | 简单问答避免复杂工具工作流 | 多条件咨询要验证每个子问题都有证据，不是命中一个文档就代表完整回答 |
| BM25+向量+RRF | 编号/术语与语义互补，融合不要求两类分数同尺度 | 当前4份文档实验没有显示召回提升，不能声称混合检索必然更好 |
| 可关闭的模型重排序 | 用模型判断候选与问题的相关性 | 增加调用、费用与超时风险；先看独立数据效果再决定开启范围 |
| 受限证据检查 | 检查证据是否足够、是否冲突；正式流程有预算与受限补检索 | 模型检查不是独立真值；本次对照仅增加assessment，没有测试完整Self-RAG补检索收益 |
| 引用验证与独立审核保留 | 不允许把错误来源当成已验证事实 | 所有live对照组均保留这层保护；实验不等于“去掉安全审核”的消融 |
| LangGraph受限流程 | 显式规划/执行和步骤预算便于复盘 | 当前主要是服务端规则选工具，不是开放自主规划Agent；简单查询可以直接工具调用 |
| MCP只读工具 | 独立工具边界、结构化协议和请求关联 | 本地进程成本和部署复杂度增加；可以切回local传输，不应为了MCP而使用MCP |
| 写操作与生成分离 | 订单事实和修改权限不由模型决定，确认/幂等/审计可验证 | 退款、改地址、改金额没有自动执行接口，不能在面试中描述为已实现 |
| 超出范围先提示 | 保留会话，由用户决定是否请求人工 | 缺证据、故障、安全问题仍有各自兜底，不能把所有handoff当作用户主动申请 |
| 全量处理追踪 | 从入口、路由、检索、工具定位失败 | Trace并不等于完整生产可观测平台；需增加告警、留存、访问控制、模型账单核对 |

## 可以关闭哪些复杂度

- `RAG_REWRITE_ENABLED=false`：关闭查询改写。
- `RAG_RERANK_ENABLED=false`：关闭模型重排序。
- `RAG_SELF_RAG_ENABLED=false`：关闭证据评估和补检索。
- `RAG_GENERATION_ENABLED=false`：返回证据原文，适合离线开发。
- `AGENT_TOOL_TRANSPORT=local`：使用本地只读工具，不启动MCP子进程。
- 灰度开关/人工接管：停止自动处理，不允许停用后偷偷改走模型。

切换配置后重启应用；更换Embedding模型必须重建索引，不能把不同模型向量混用。关闭后要复跑相同评测，不能只看服务是否启动。

## 一个可讲清楚的失败案例

问题：“耳机还有现货吗”。候选参考处理是查询实时商品服务，但规则路由走了FAQ。根因是策略层没有覆盖“现货”的业务事实表达，不是生成模型能力不足。修改方向是给实时事实增加可靠语义/意图判断，缺商品标识先澄清；不能从说明文档编造库存。此次保留原始失败报告，尚未用这批候选测试题调优生产路由。

面试可以追问：为什么不用大模型分类所有请求？回答应是规则作为便宜基线，模型分类只有在真实开发集证明增益和成本可接受时加入，并保留低置信度澄清/明确人工申请。
